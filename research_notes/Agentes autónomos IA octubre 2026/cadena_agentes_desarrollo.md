# Cadena de agentes para desarrollo: investigación → arquitectura por sistema → implementación (estado a octubre de 2026)

Notas de investigación compiladas el 2026-10-01. Todas las afirmaciones llevan fecha de la fuente cuando la fuente la indica; cuando no, se marca "(consultado 2026-10-01)". Sólo fuentes primarias (documentación oficial, blogs de ingeniería de los proveedores, papers), salvo donde se indica explícitamente "fuente secundaria". Las citas textuales se mantienen en el idioma original. Al final de cada sección se marca con **[Equipo pequeño]** lo específicamente útil para un equipo pequeño de desarrollo Odoo/OpenERP (caso del usuario: varios sistemas, uno llamado "Concord", agentes de código ya existentes).

Nota de contexto para el redactor: el usuario quiere una cadena (1) agente de investigación web que compile soluciones probadas/benchmarks para una nueva funcionalidad → (2) agente de arquitectura con conocimiento profundo de un sistema concreto que traduzca esa investigación a un diseño para ese sistema → (3) entrega a agentes de código. El hallazgo transversal más importante: **ningún proveedor documenta esta cadena exacta como producto**, pero cada eslabón tiene herramientas y guías primarias maduras, y el patrón "spec → plan/diseño → tareas → implementación" (Spec Kit, Kiro, Claude Code plan mode) es hoy la forma estándar de conectar los eslabones 2 y 3.

## Pregunta 1: ¿Qué recomiendan oficialmente Anthropic, OpenAI, Google y Microsoft (2025-2026) para diseñar pipelines multi-agente, y qué fallas documentan?

### Takeaway
Los cuatro proveedores convergen en: empezar con un agente simple, añadir agentes sólo cuando la tarea se paraleliza o excede una ventana de contexto, dar a cada agente un contexto curado ("context engineering"), separar investigación/planificación de implementación, y cerrar el bucle con verificación automática más revisión humana. Las fallas documentadas son coste de tokens (hasta 15x), decisiones contradictorias entre subagentes que no comparten contexto, "context rot", y la fragilidad de los sistemas multi-agente para código con muchas dependencias.

### Cited Findings

**Anthropic — patrones de orquestación y cuándo usarlos**
- "Building effective agents" (2024-12-19) define cinco workflows: prompt chaining, routing, parallelization (sectioning/voting), orchestrator-workers ("you can't predict the subtasks needed") y evaluator-optimizer ("we have clear evaluation criteria, and when iterative refinement provides measurable value"). Principios: simplicidad, transparencia de los pasos de planificación, documentación y testing cuidadosos de las herramientas. Advertencias: los sistemas agénticos "trade latency and cost for better task performance", riesgo de "compounding errors", y los frameworks "obscure underlying prompts and responses, making them harder to debug". Sobre código: los agentes rinden bien porque el código es "verifiable through automated tests", pero "human review remains crucial for ensuring solutions align with broader system requirements". — [Anthropic Engineering](https://www.anthropic.com/engineering/building-effective-agents)
- "How we built our multi-agent research system" (2025-06-13): arquitectura orchestrator-worker con lead agent (Opus 4), subagentes paralelos (Sonnet 4) y un agente de citas. Resultado interno: 90.2% de mejora frente a Opus 4 single-agent. Coste: los sistemas multi-agente usan ~15x los tokens de un chat; el uso de tokens explica el 80% de la varianza en BrowseComp. Ocho principios de prompting para el orquestador (delegación detallada con límites claros, reglas de escalado de esfuerzo según complejidad, "start wide, then narrow down", thinking como scratchpad, llamadas paralelas a herramientas). Evaluación: LLM-as-judge con rúbrica de "factual accuracy… citation accuracy… completeness… source quality… tool efficiency", empezando con ~20 consultas, más evaluación humana. Fiabilidad en producción: "Minor changes cascade into large behavioral changes", errores que se acumulan, no-determinismo; mitigado con ejecución durable con checkpoints, tracing y "rainbow deployments". Límite explícito: "some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today", en particular tareas de código con poca paralelización. Idóneo para "heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools". — [Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- "Effective context engineering for AI agents" (2025-09-29): define context engineering como "the set of strategies for curating and maintaining the optimal set of tokens (information) during LLM inference". Recomienda prompts a la "right altitude", herramientas "self-contained, robust to error, and extremely clear", ejemplos canónicos diversos, y para tareas largas tres técnicas: compaction, structured note-taking (notas persistentes fuera del contexto) y sub-agent architectures que devuelven resúmenes condensados. Recomienda recuperación "just in time" manteniendo "lightweight identifiers (file paths, stored queries, web links, etc.)". Documenta el "context rot": "as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases". — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Claude Code best practices (consultado 2026-10-01): el flujo recomendado es "Explore first, then plan, then code" en cuatro fases (Explore en plan mode → Plan → Implement → Commit), con la advertencia "If you could describe the diff in one sentence, skip the plan". Para funcionalidades grandes: "have Claude interview you first… then write a complete spec to SPEC.md", y "Once the spec is complete, start a fresh session to execute it". Las specs útiles "name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step". Patrón Writer/Reviewer con dos sesiones: "A fresh context improves code review since Claude won't be biased toward code it just wrote". Recomienda "Add an adversarial review step" con un subagente que ve sólo el diff y los criterios, con la advertencia de que "A reviewer prompted to find gaps will usually report some, even when the work is sound". Fallas comunes documentadas: "kitchen sink session", "correcting over and over", "over-specified CLAUDE.md", "trust-then-verify gap", "infinite exploration". — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Guía "Steering Claude Code" (2026-06-18): siete mecanismos (CLAUDE.md, rules, skills, subagents, hooks, output styles, append system prompt). "Keep CLAUDE.md under 200 lines, give it an owner, and review changes to it like code." Las conductas "Every time X, always do Y" y "Never do this" no deben ir en CLAUDE.md: "A real guardrail needs to be deterministic, and the enforcement methods are hooks and permissions." Subagentes: "The only thing that returns to your main session is the subagent's final message", anidables hasta cinco niveles. — [Claude Blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- "A harness for every task: dynamic workflows in Claude Code" (2026-06-02): primitivas `agent()`, `parallel()`, `pipeline()`; seis patrones: classify-and-act, fan-out-and-synthesize, adversarial verification, generate-and-filter, tournament, loop until done. Atacan "agentic laziness", sesgo auto-preferencial y goal drift. Advertencia: "workflows are not needed for every task and may end up using significantly more tokens." — [Claude Blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- Agent Skills (2025-10-16): "organized folders of instructions, scripts, and resources that agents can discover and load dynamically"; revelación progresiva en tres niveles (nombre+descripción al arrancar → SKILL.md completo al activarse → archivos enlazados bajo demanda). Desarrollo "evaluation-first": "Identify specific gaps in your agents' capabilities by running them on representative tasks and observing where they struggle". Seguridad: "install skills only from trusted sources". — [Anthropic Engineering](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)

**OpenAI**
- "A practical guide to building agents" (PDF, 2025): single-agent como punto de partida por defecto; pasar a multi-agente cuando la lógica es demasiado compleja o hay "tool overload". Dos patrones: **manager** (un agente central orquesta especialistas mediante tool calls y sintetiza) y **decentralized** (handoffs entre agentes de igual nivel). Guardrails en capas: relevance classifier, safety classifier, tool safeguards, y disparadores de intervención humana por umbrales de fallo y acciones de alto riesgo. — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf); descripción de ambos patrones ("In the manager pattern, edges represent tool calls whereas in the decentralized pattern, edges represent handoffs") en la página de la guía — [OpenAI](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)
- Agents SDK — handoffs: "Handoffs are represented as tools to the LLM. So if there's a handoff to an agent named `Refund Agent`, the tool would be named `transfer_to_refund_agent`"; input filters para recortar el historial que ve el agente receptor; `RECOMMENDED_PROMPT_PREFIX` para que el modelo entienda los handoffs; "Register one handoff per destination if there are multiple possible specialists". — [OpenAI Agents SDK docs](https://openai.github.io/openai-agents-python/handoffs/)
- Deep Research API: "You must include at least one data source: web search, remote MCP servers, or file search with vector stores"; herramientas soportadas: `web_search_preview`, file search (máx. dos vector stores), code interpreter, MCP remoto (debe implementar interfaces search y fetch, `require_approval: never`); "Other tools, such as function calling, are not supported". Se recomienda background mode porque "Deep research requests can take a long time". "Deep research via the Responses API does not include a clarification or prompt rewriting step", por lo que sugieren usar un modelo rápido para aclarar/reescribir el prompt antes. Seguridad MCP: "Only connect to trusted MCP servers", "Log and review tool calls and model messages", y un flujo por fases: primero investigación web sin MCP, luego MCP con datos privados. La guía indica que `o3-deep-research` y `o4-mini-deep-research` se apagan el 2026-07-23 con `gpt-5.6-sol` como reemplazo. — [OpenAI Developers](https://developers.openai.com/api/docs/guides/deep-research). **Conflicto**: la página del modelo `o3-deep-research` (consultada 2026-10-01) no muestra fecha de deprecación y sigue listando precio $10/$2.50/$40 por MTok con 200k de contexto — [OpenAI Developers](https://developers.openai.com/api/docs/models/o3-deep-research).
- "Harness engineering: leveraging Codex in an agent-first world" (2026-02): OpenAI reporta haber "built and shipped a beta product containing roughly a million lines of code without any manually written source code" en cinco meses; la documentación interna vive en "a structured docs directory containing maps, execution plans, and design specifications" como fuente única de verdad para los agentes; "OpenAI enforces architectural boundaries and dependency layers across domains through mechanical rules and structural tests" (capas Types → Config → Repo → Service → Runtime → UI). — resumen vía [InfoQ (fuente secundaria, 2026-02-21)](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex); el original [openai.com/index/harness-engineering](https://openai.com/index/harness-engineering/) devolvió 403 al consultarse. Fuentes secundarias adicionales atribuyen al post cifras de ~1,500 PRs, 7 ingenieros, un AGENTS.md de ~100 líneas que actúa como índice hacia DESIGN.md/ARCHITECTURE.md/exec-plans, y un agente de "doc-gardening" que abre PRs para corregir docs obsoletos — [saascity.io (secundaria)](https://saascity.io/blog/harness-engineering-codex-agent-first-openai-2026). No pude verificar estas cifras en el original.

**Google**
- ADK (consultado 2026-10-01): "Template Workflows" (sequential, loop, parallel, custom), "Graph-based Workflows (ADK 2.0 and higher)" que combinan agentes y nodos determinísticos con bifurcaciones, "Collaborative Workflows" ("a single agent to act in a dynamic coordinator role… with a set of specified sub-agents") y "Dynamic Workflows" programáticos. Beneficios declarados: predictability, reliability, structure. — [ADK docs](https://adk.dev/workflows/)
- Gemini Deep Research agent (consultado 2026-10-01): dos variantes, `deep-research-preview-04-2026` ("Designed for speed and efficiency") y `deep-research-max-preview-04-2026` ("Maximum comprehensiveness for automated context gathering and synthesis"); "exclusively available using the Interactions API"; requiere `background=true`; soporta MCP servers (name, url, headers, allowed_tools), entradas multimodales, planificación colaborativa multi-turno, y produce "detailed, cited reports". Herramientas por defecto: Google Search, URL Context, Code Execution; File Search para corpus propio. — [Google AI for Developers](https://ai.google.dev/gemini-api/docs/deep-research)
- Jules (consultado 2026-10-01): agente asíncrono que "clones your code, installs dependencies, and modifies files" en una VM, genera un plan que el usuario "can review and approve… before any code changes are made", y "automatically looks for a file named AGENTS.md in the root of your repository". — [Jules docs](https://jules.google/docs)

**Microsoft**
- Agent Framework (overview fechado 2026-07-29, actualizado 2026-08-25): sucesor directo de Semantic Kernel y AutoGen; cuatro áreas: Agents, Harness Agent ("planning and todo tracking, context compaction, file access and memory, don't-ask-again tool approval, and observability"), Workflows (grafo), Integrations. Regla explícita: "If you can write a function to handle the task, do that instead of using an AI agent." Tabla agente vs workflow: workflow cuando "The process has well-defined steps" y "Multiple agents or functions must coordinate". — [Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/overview/agent-framework-overview)
- Orquestaciones (2026-02-12): Sequential, Concurrent, Handoff, Group Chat, Magentic ("A manager agent dynamically coordinates specialized agents"); human-in-the-loop mediante "approval-required tools that pause the workflow for human review before execution". — [Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/user-guide/workflows/orchestrations/overview)
- Spec-Driven Development (Microsoft for Developers, 2026-06-10, Apoorv Gupta): "Spec-Driven Development (SDD) is a spec-first approach. Teams define common guardrails, requirements, constraints, acceptance criteria, and edge cases up front, then use AI to generate code, tests, and supporting artifacts from that shared context." Ciclo de siete etapas de Spec Kit: Constitution, Specify, Clarify, Plan, Tasks, Implement, Validate. "spec quality = output quality". — [Microsoft Developer Blog](https://developer.microsoft.com/blog/spec-driven-development-ai-native-engineering/)

**Voz disidente relevante (Cognition)**
- "Don't Build Multi-Agents" (2025-06-12, Walden Yan): dos principios: "Share context, and share full agent traces, not just individual messages" y "Actions carry implicit decisions, and conflicting decisions carry bad results". Recomienda un agente lineal single-threaded y, para tareas largas, un LLM que comprima el historial. Observa que los subagentes de Claude Code "lack context from the main agent that would otherwise be needed to do anything beyond answering a well-defined question", es decir, se usan para preguntas acotadas, no para codificación paralela. — [Cognition](https://cognition.com/blog/dont-build-multi-agents)

**Frameworks de terceros (referencia)**
- LangChain/LangGraph (consultado 2026-10-01) lista cinco patrones: Subagents ("A main agent coordinates subagents as tools"), Handoffs (cambio de agente vía estado), Skills ("Specialized prompts and knowledge loaded on-demand. A single agent stays in control"), Router, Custom Workflow. "At the center of multi-agent design is context engineering—deciding what information each agent sees." — [LangChain docs](https://docs.langchain.com/oss/python/langchain/multi-agent)

### Inferences
- La cadena del usuario encaja en lo que los proveedores sí recomiendan: la investigación (eslabón 1) es un caso de "heavy parallelization + información que excede una ventana" (ideal para multi-agente según Anthropic); la implementación (eslabón 3) es el caso donde Anthropic y Cognition desaconsejan paralelismo ciego por dependencias. Diseño coherente con las guías: multi-agente para investigar, un único hilo (o Writer/Reviewer) para implementar.
- El eslabón 2 ("agente de arquitectura por sistema") es, en términos de los proveedores, un paso de "Plan"/"design.md" con contexto curado del sistema; ninguna guía lo trata como agente autónomo con memoria propia, pero Claude Code lo habilita con subagentes con `memory: project` y skills por sistema (ver Pregunta 3).
- Los handoffs entre eslabones deben ser **artefactos escritos** (informe de investigación → design.md/SPEC.md → tasks.md), no historial conversacional: así lo hacen Spec Kit, Kiro, el flujo "interview → SPEC.md → fresh session" de Anthropic y el `docs/` de OpenAI.

### Gaps
- No encontré un documento oficial de ningún proveedor que describa la cadena "research agent → system-architect agent → coding agent" como tal; lo anterior es composición de guías.
- No pude leer el original de "Harness engineering" (403); las cifras detalladas provienen de fuentes secundarias.

**[Equipo pequeño]** Aplicar la regla de Anthropic/OpenAI/Microsoft "empieza con un agente": un solo Claude Code (o Codex) en plan mode que investigue, escriba SPEC.md y luego implemente en sesión limpia ya materializa la cadena sin infraestructura. Añadir subagentes sólo para la investigación web (paralelizable) y para la revisión adversarial.

## Pregunta 2: ¿Qué evidencia concreta (casos, blogs, papers) existe sobre cadenas investigar → diseñar → implementar y sus resultados?

### Takeaway
Hay evidencia primaria sólida de que (a) separar plan/diseño de implementación y (b) alimentar al generador con documentación arquitectónica mejoran corrección y conformidad; los casos más fuertes son el paper ICSE 2026 de Cervantes/Kazman/Cai, el sistema Agyn (72.2% en SWE-bench 500 con roles de research/implementation/review), CodeNib (79 vs 66 issues resueltos con contexto de repo estructurado), y los reportes de OpenAI (harness engineering) y Microsoft (SDD brownfield). La evidencia sobre el eslabón de **investigación web de mercado** previa al diseño es, en cambio, casi inexistente en fuentes primarias.

### Cited Findings
- Paper ICSE 2026 (Designing workshop, 2026-04-13), "Improving LLM-assisted code generation through the use of architectural documents and implementation plans" (Humberto Cervantes, Rick Kazman, Yuanfang Cai): flujo donde "the LLM synthesizes an implementation plan from requirements and an architecture document, and then generates code with human oversight"; tres experimentos con agente ReAct; conclusión: incorporar documentación arquitectónica mejora sustancialmente la conformidad arquitectónica, y añadir un plan de implementación explícito mejora además la corrección funcional y la modularidad (medida con DV8). — [ICSE 2026](https://conf.researchr.org/details/icse-2026/designing-2026-papers/2/Improving-LLM-assisted-code-generation-through-the-use-of-architectural-documents-and); DOI [10.1145/3786152.3788588](https://dl.acm.org/doi/10.1145/3786152.3788588)
- Agyn (arXiv 2602.01465, enviado 2026-02-01, Benkovich & Valkov): "specialized agents to roles such as coordination, research, implementation, and review", sandboxes aislados, comunicación estructurada; flujo de "analysis, task specification, pull request creation, and iterative review… without any human intervention"; "resolves 72.2% of tasks" en SWE-bench 500, "outperforming single-agent baselines using comparable language models"; "the system was designed for real production use and was not tuned for SWE-bench"; conclusión: "future progress may depend as much on organizational design and agent infrastructure as on model improvements." — [arXiv](https://arxiv.org/abs/2602.01465)
- CodeNib (arXiv 2607.25431, 2026-07-28, rev. 2026-09-28): sistema que compila "lexical, dense, and structural views of one commit behind a single manifest" para agentes; 78/90 ejecuciones completadas vs 65 sin él; en SWE-bench Verified resolvió 79 issues vs 66 (exploración bajo demanda) y 56 (repo map de Aider); políticas de contexto con "50–87% fewer tokens than grep/read"; hallazgo contraintuitivo: el contexto rinde mejor cuando se "retira" después de la lectura inicial del agente. — [arXiv](https://arxiv.org/abs/2607.25431)
- MAAD (arXiv 2507.21382, 2025-07-30, Li, Zhang, Zhou, Liang, Sun, Xuan, Jin, Liu; TOSEM): automatiza el diseño arquitectónico con cuatro roles (Analyst, Modeler, Designer, Evaluator) alimentados por una base de conocimiento arquitectónico (patrones, decisiones). — [arXiv PDF](https://arxiv.org/pdf/2507.21382). *Nota: la extracción automática del PDF no devolvió los resultados cuantitativos; tratar la descripción de roles como verificada y los resultados como no verificados.*
- "Effective Strategies for Asynchronous Software Engineering Agents" (arXiv 2603.21489, Geng & Neubig, 2026): identifica como estrategias efectivas la calidad de la especificación, planificación y contexto, verificación y revisión. — [arXiv PDF](https://arxiv.org/pdf/2603.21489). *Nota: la extracción del PDF fue parcial; no pude recuperar las cifras.*
- "Developing LLM-based Multi-Agent Systems in Software Engineering: A Mixed-Method Experience Report" (arXiv 2608.11965, 2026-08-12): los frameworks MAS "provide a good coverage of fundamental components of MAS, though advanced features such as telemetry of agents are still missing"; los desarrolladores deben "carefully select the right technology, devise proper coordination rules, and design specific roles". — [arXiv](https://arxiv.org/abs/2608.11965)
- Microsoft SDD brownfield (2026-06-10): un equipo que capturó patrones reutilizables en specs parametrizadas "reduced onboarding time from 2–3 weeks to a few days". — [Microsoft Developer Blog](https://developer.microsoft.com/blog/spec-driven-development-ai-native-engineering/)
- GitHub Spec Kit (2025-09-02): justifica la cadena spec→plan→tasks→implement porque los LLM "excel at pattern completion, but not at mind reading. A vague prompt like 'add photo sharing to my app' forces the model to guess at potentially thousands of unstated requirements"; para sistemas legados propone "capture the essential business logic in a modern spec, design a fresh architecture in the plan, and then let the AI rebuild the system". — [GitHub Blog](https://github.blog/news-insights/product-news/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- Anthropic multi-agent research (2025-06-13): 90.2% de mejora en investigación con orquestador+subagentes, a costa de ~15x tokens (ver Pregunta 1). — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- OpenAI harness engineering (2026-02): ~1M LOC sin código manual en 5 meses; documentación estructurada como fuente de verdad; límites arquitectónicos por reglas mecánicas. — [InfoQ (secundaria)](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)
- Claude Code dynamic workflows (2026-06-02): aplicaciones citadas: reescritura Zig→Rust de Bun, deep research, migraciones de código a escala empresarial. — [Claude Blog](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)
- Afirmaciones **no verificadas** (fuentes secundarias halladas por búsqueda): "GitHub reports that teams using Spec Kit on internal projects ship features with roughly an order-of-magnitude fewer 'regenerate from scratch' cycles" y "AWS Kiro documents real customer cases where 40-hour features were shipped in under 8 hours" — [thebcms.com (secundaria)](https://www.thebcms.com/blog/spec-driven-development/); caso personal "13 apps en 70 días" con 28 specs en repo — [felipefontoura.com (secundaria)](https://felipefontoura.com/articles/spec-driven-development-case-study/). No encontré estas cifras en fuentes de GitHub o AWS.

### Inferences
- La evidencia académica (ICSE 2026, CodeNib) y la industrial (OpenAI, Microsoft) coinciden en que el **documento de arquitectura + plan explícito** es la palanca de calidad, exactamente la salida que debería producir el agente de arquitectura del usuario.
- Agyn demuestra que una organización por roles (research/implementation/review) supera a un agente único con el mismo modelo, lo que respalda el diseño en cadena; pero su "research" es investigación del repositorio, no de mercado.

### Gaps
- No encontré papers ni blogs primarios que midan el efecto de un paso de **investigación web de mercado/benchmarks** antes del diseño de software. La evidencia de deep research se limita a tareas de investigación (BrowseComp, evaluaciones internas), no a su impacto en el código resultante.
- Las cifras de Spec Kit/Kiro ("3–10x", "40 h → 8 h") no están respaldadas por fuentes primarias localizadas.

**[Equipo pequeño]** El resultado más transferible es el de ICSE 2026: basta un documento de arquitectura por sistema (p. ej., `docs/ARCHITECTURE.md` de Concord) y un plan de implementación generado antes de codificar para mejorar conformidad y corrección, sin orquestación compleja.

## Pregunta 3: ¿Cómo dan los equipos a un agente conocimiento durable y preciso de la arquitectura de un sistema concreto, y qué funciona mejor (RAG, MCP, docs en repo, skills)?

### Takeaway
La práctica dominante en 2026 es **documentación en el repo con revelación progresiva** (CLAUDE.md/AGENTS.md cortos que apuntan a docs de arquitectura, skills y rules por ruta), complementada con **búsqueda agéntica just-in-time** sobre el código y, para datos vivos, **servidores MCP**. La evidencia (CodeNib, ICSE 2026, harness engineering) favorece el contexto estructurado y acotado sobre volcar todo en el prompt; no encontré fuentes primarias que recomienden fine-tuning para conocimiento de arquitectura.

### Cited Findings

**Archivos de instrucciones en el repositorio**
- CLAUDE.md: "a special file that Claude reads at the start of every conversation"; incluir "Architectural decisions specific to your project", comandos, convenciones y "Common gotchas"; excluir "Detailed API documentation (link to docs instead)" y "File-by-file descriptions of the codebase". "Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Soporta importación con `@path/to/import`. Para conocimiento de dominio que sólo aplica a veces: "use skills instead. Claude loads them on demand without bloating every conversation." — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Rules con `paths:` frontmatter: "a rule scoped to `src/api/**` stays out of context during a docs-only session"; subdirectorios con CLAUDE.md propios en monorepos. — [Claude Blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more)
- Subagentes de Claude Code (consultado 2026-10-01): archivos Markdown en `.claude/agents/` con frontmatter `name`, `description`, `tools`, `model`, `permissionMode`, `skills` (precarga de skills), `memory` (`user`/`project`/`local`; `project` → `.claude/agent-memory/<name>/`, versionado), `maxTurns`, `hooks`, `mcpServers`, `isolation: worktree`, `omitClaudeMd`. Con memoria: "update your agent memory with patterns, conventions, and recurring issues you discover". El subagente recibe CLAUDE.md, snapshot de git y skills precargadas, pero no el historial de la conversación principal. ### Inferences
- La "arquitectura de un sistema" se materializa hoy como **capas**: (1) CLAUDE.md/AGENTS.md ≤200 líneas con las decisiones y gotchas; (2) `docs/ARCHITECTURE.md` + ADRs enlazados (revelación progresiva); (3) skills/rules por módulo o ruta; (4) subagente "arquitecto-Concord" con `memory: project` que acumula patrones; (5) MCP sólo para datos vivos (esquema real de la BD de Odoo, módulos instalados, registros).

- Fine-tuning no aparece en ninguna guía primaria de 2025-2026 como vía para conocimiento de arquitectura; todo el peso está en context engineering.

### Gaps
- No hallé estudios primarios comparando RAG vectorial vs búsqueda agéntica vs wikis generadas específicamente para "conocimiento arquitectónico"; CodeNib es lo más cercano.
- No hallé fuente primaria sobre fine-tuning vs context engineering para este fin.
- Documentación oficial de Devin Knowledge/DeepWiki no accesible (404); lo citado es secundario.

**[Equipo pequeño]** Un repo por sistema (p. ej., Concord) con: `CLAUDE.md` + `AGENTS.md` cortos (ambos, para servir a Claude Code y a Codex/Copilot/Jules), `docs/architecture.md` + `docs/adr/`, `.claude/skills/odoo-concord-conventions/SKILL.md`, y `.claude/agents/arquitecto-concord.md` con `memory: project` y `tools: Read, Grep, Glob`. Esto no requiere infraestructura adicional y es compatible con los agentes de código que ya usan.

## Pregunta 5: ¿Cómo se evalúa la salida de estas cadenas (métricas, frameworks de evals, gates humanos, CI)?

### Takeaway
Las guías oficiales recomiendan combinar graders de código (tests, build, linters) con LLM-as-judge calibrado contra humanos y lectura de transcripts; para agentes de código, el gate principal es un chequeo ejecutable que el agente puede correr (tests, `/goal`, Stop hooks) más una revisión adversarial en contexto limpio y aprobación humana del PR. OpenAI Evals API se apaga el 2026-11-30; Promptfoo, LangSmith y Braintrust siguen activos.

### Cited Findings
- Anthropic, "Demystifying evals for AI agents" (2026-01-09): eval = "a test for an AI system: give an AI an input, then apply grading logic to its output to measure success"; distingue transcript ("the complete record of a trial, including outputs, tool calls, reasoning, intermediate results") de outcome ("the final state in the environment at the end of the trial"); tres tipos de grader: code-based (rápido, objetivo, frágil), model-based/LLM-as-judge (flexible, no determinista, requiere calibración humana), humano (gold standard, caro). Para agentes de código: "well-specified tasks, stable test environments, and thorough tests for the generated code", combinando tests unitarios deterministas, rúbricas de calidad y análisis de transcript. Pitfalls: saturación ("An eval at 100% tracks regressions but provides no signal for improvement"), y la diferencia pass@k ("at least one correct solution in k attempts") vs pass^k ("the probability that all k trials succeed"). Para empezar: 20–50 tareas realistas derivadas de fallos reales, con solución de referencia, entornos aislados por trial y lectura regular de transcripts. — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Anthropic multi-agent research: LLM-as-judge de una sola llamada con rúbrica (accuracy, citation accuracy, completeness, source quality, tool efficiency); evaluación humana para sesgos. — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- Claude Code, gates ejecutables (consultado 2026-10-01): "Give Claude a check it can run: tests, a build, a screenshot to compare"; escalera de gates: en el prompt → `/goal` (evaluador independiente re-chequea cada turno) → Stop hook determinista ("blocks the turn from ending until it passes") → "verification subagent" que intenta refutar el resultado; "Have Claude show evidence rather than asserting success"; `/code-review` revisa el diff en subagente limpio. — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Hooks de Claude Code (consultado 2026-10-01): eventos `SessionStart`, `UserPromptSubmit`, `PreToolUse` (puede bloquear), `PostToolUse`, `PostToolUseFailure`, `PostToolBatch`, `Stop` (puede impedir que termine), `StopFailure`, `SessionEnd`; "Exit 2 means a blocking error… even a JSON permissionDecision of 'allow' can't override it"; tipos de handler: command, http, mcp_tool, prompt, agent (experimental); advertencia: "Don't count on a stalled hook to act as a gate". — [Claude Code Docs](https://code.claude.com/docs/en/hooks)
- Claude Code GitHub Actions: ejecución sólo por usuarios con write access y actores humanos (anti-bucle con bots); revisión automática de PRs con el plugin `code-review` y `--comment`; controles de coste `--max-turns`, timeouts, concurrency. — [Claude Code Docs](https://code.claude.com/docs/en/github-actions)
- OpenAI guardrails: capas (relevance, safety, tool safeguards) y "human intervention triggers" por umbrales de fallo y acciones de alto riesgo. — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)
- OpenAI Evals API: evals con `data_source_config` + `testing_criteria` (graders como `string_check`), ficheros JSONL con `purpose: "evals"`, ejecución asíncrona con `result_counts`; aviso: "Evals will become read-only for existing users on October 31, 2026, and the platform is scheduled to shut down on November 30, 2026." — [OpenAI Developers](https://developers.openai.com/api/docs/guides/evals)
- Promptfoo: "an open-source CLI and library for evaluating and red-teaming LLM apps"; 25.6k estrellas en GitHub; uso "as a CLI, library, or in CI/CD" (GitHub Actions); red teaming con informes de vulnerabilidad. — [Promptfoo Docs](https://www.promptfoo.dev/docs/intro/)
- LangSmith (página de producto, vía búsqueda): evals offline sobre datasets, online sobre tráfico, LLM-as-judge; "Align Evals helps you calibrate LLM-as-judge scorers against human feedback". — [LangChain (vendor)](https://www.langchain.com/langsmith/evaluation). Braintrust (artículo del vendor): "traces multi-step workflows and scores both intermediate steps and final outputs"; distingue checks de código (formato, longitud, esquema) de LLM-as-judge (helpfulness, grounding). — [Braintrust (vendor)](https://www.braintrust.dev/articles/what-is-llm-as-a-judge)
- Gates humanos integrados en los agentes: Jules exige aprobar el plan antes de cambiar código — [Jules Docs](https://jules.google/docs); Copilot coding agent abre exactamente un PR por tarea y el desarrollador decide crearlo/mergearlo — [GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent); Microsoft Agent Framework pausa workflows con "approval-required tools" — [Microsoft Learn](https://learn.microsoft.com/en-us/agent-framework/user-guide/workflows/orchestrations/overview); Kiro y Spec Kit insertan checkpoints de validación entre specify/plan/tasks/implement (Spec Kit añade `/speckit-converge` para verificar) — [GitHub](https://github.com/github/spec-kit), [Kiro](https://kiro.dev/docs/specs/).
- Benchmarks de referencia usados en papers: SWE-bench Verified (CodeNib 79 issues) y SWE-bench 500 (Agyn 72.2%). — [arXiv](https://arxiv.org/abs/2607.25431), [arXiv](https://arxiv.org/abs/2602.01465)

### Inferences
- Para la cadena del usuario, los puntos de evaluación naturales son tres artefactos: (1) informe de investigación → LLM-as-judge con la rúbrica de Anthropic (accuracy/citations/completeness/source quality) + muestreo humano; (2) design.md → revisión humana obligatoria más un subagente que compruebe conformidad con `docs/architecture.md`; (3) código → tests de módulo Odoo + pylint-odoo en PostToolUse/Stop hooks + `/code-review` + aprobación del PR.
- Dado el cierre de OpenAI Evals API, la opción abierta y neutral de proveedor es Promptfoo; LangSmith/Braintrust aportan trazas si se adopta un framework de orquestación.

### Gaps
- No encontré benchmarks ni métricas publicadas específicas para evaluar la calidad de un "documento de arquitectura" generado por agentes (más allá de la conformidad medida en ICSE 2026).
- Precios actuales de LangSmith y Braintrust no consultados en fuentes primarias.

**[Equipo pequeño]** El gate más barato y efectivo según las guías: tests ejecutables + hook `Stop` que corre `pytest`/tests de Odoo y `pylint-odoo` + revisión del PR por un humano; añadir 20–50 tareas reales de Concord como set de evals para medir regresiones cuando cambien de modelo o de prompts.

## Resumen operativo para la cadena del usuario (síntesis de las fuentes anteriores)

1. **Agente investigador** (eslabón 1): orquestador + subagentes de búsqueda web (patrón Anthropic), o un deep-research gestionado (OpenAI Responses con `web_search_preview`/MCP; Gemini `deep-research-*` vía Interactions API; Perplexity `sonar-deep-research`). Reescribir/aclarar el prompt con un modelo rápido antes (recomendación OpenAI); salida = informe con citas y rúbrica de calidad (LLM-as-judge). Presupuestar ~15x tokens frente a un chat.
2. **Agente arquitecto por sistema** (eslabón 2): subagente Claude Code (`.claude/agents/arquitecto-concord.md`, `memory: project`, sólo lectura) que carga `docs/architecture.md`, ADRs y skills del sistema; produce `design.md` + `tasks.md` al estilo Kiro/Spec Kit; evidencia ICSE 2026 de que documento de arquitectura + plan mejoran conformidad y corrección. Gate humano aquí (es el punto de mayor apalancamiento según Spec Kit: "spec quality = output quality").
3. **Agentes de código** (eslabón 3): entregar `tasks.md` como artefacto; ejecutar en sesión limpia (Anthropic), un hilo por tarea (Cognition), Writer/Reviewer o revisión adversarial; hooks deterministas (tests, lint) y PR con aprobación humana; cualquier agente que lea AGENTS.md (Codex, Copilot, Jules, Cursor, Devin) puede ser el ejecutor si el repo mantiene AGENTS.md y CLAUDE.md sincronizados.
